# HanaME の質問に回答する

HanaME は、AI が書いた .md を人が読みながら、気になった文に質問を書き込むビューアです。質問と空の回答欄は .md ファイルの中にあります。その回答欄に回答を書き込むのが、このスキルの仕事です。

## 書式

```markdown
## 見出し

> [!ANSWER] Q1
>

本文。……対象の文。……

> [!QUESTION] Q1 対象:「対象の文」
> 質問の文
```

- 回答欄 `> [!ANSWER] Qn` は、質問の対象がある節の見出しの直下にあります。質問 `> [!QUESTION] Qn` は、対象の段落の直後にあります。番号が同じものが組です。
- 回答欄と質問は離れた場所にあることが多いです。同じ番号どうしが組だと考えてください。
- 回答欄の中身が `>` だけの行なら未回答です。回答欄の後ろにある空行は、本文との区切りなので残します。
- 回答への追加の質問は `Q1-1`、さらにその追加は `Q1-1-1` という番号になります。親の回答欄の後ろに、質問と回答欄が組で並びます。

## 手順

1. **未回答の質問を探す。** 頼まれたフォルダ（指定がなければ作業フォルダ）で `haname prompt` を実行します。未回答の質問があるファイルと番号が一覧で出ます。
   - 「未回答の質問はありません。」と出たら、そう伝えて終わります。
   - 出力に書かれたルールはこのスキルと同じものです。食い違うときは、入っている haname の版に合った `haname prompt` の出力を優先します。
   - 一覧のファイルが見つからないときや、頼まれたフォルダの外のファイルが出たときは、回答せずにユーザーに確かめます。
   - `haname` コマンドが無いときは、`> [!ANSWER]` を含む .md を検索し、中身が空の回答欄を探します。`npx haname` は使わないでください。haname は npm に公開されていないので、同じ名前の別のパッケージを実行してしまうおそれがあります。
2. **ファイルを読む。** ファイルごとに全体を読み、質問ごとに次をつかみます。
   - 対象の文と、その前後の本文、属している見出し
   - 追加の質問なら、親の質問とその回答
3. **回答を考える。** 本文だけで答えられないときは、リポジトリのコードや他の資料を読んで確かめます。確かめられないことは、最後に1文で「〜は確かめていません」と書きます。
   - 追加の質問（`Q1-1` など）には、親の回答で言ったことを繰り返さず、聞かれた点だけに答えます。
4. **回答欄に書き込む。** `> [!ANSWER] Qn` の次にある `>` だけの行を消し、そこに回答を書きます。回答の1行目は `> ` で始め（`>>` にしない）、最後の行の後ろに `>` だけの行は残しません。ファイル全体を書き直さず、その部分だけを編集します。
5. **確かめる。** もう一度 `haname prompt` を実行し、答えた質問が残っていないことを確かめます。
6. **報告する。** チャットでは、どのファイルのどの番号に回答したかだけを短く伝えます。回答の中身は繰り返しません（ユーザーは HanaME で読みます）。質問と関係のない本文の誤りに気付いたときは、回答には書かず、この報告で1行ずつ伝えます。

## 守ること

- 変えてよいのは、未回答の回答欄の中身だけです。本文・見出し・`[!QUESTION]`・回答済みの `[!ANSWER]` と、ブロックの並び順は変えません。
- 質問や回答欄を新しく作ったり、消したり、動かしたりしません。
- 回答の行はすべて `> ` で始めます。段落の区切りは `>` だけの行にします。`> ` で始まらない行や空行があると、そこで回答欄が終わったと見なされます。
- 回答の中に、`[!QUESTION]` や `[!ANSWER]` で始まる行を書きません。HanaME がブロックの区切りと誤って読みます。
- 読み手は前提知識が少ない人です。結論を最初の1〜2文で言い、専門用語はかみ砕いて説明します。補足は必要な分だけにして、1つの回答は長くても10行ほどに収めます。10行を超えそうなときは、下の「長くなる回答」に従います。
- 質問に関わる本文の誤りに気付いたら、回答の中で指摘します。本文は直しません。

## 長くなる回答

理解してもらうのに10行を超える説明が要るときは、削って10行に縮めないでください。HanaME は、要約せずに読んで理解するための道具です。代わりに、その質問のための新しい .md を提案します。10行は、`>` だけの区切りの行を除いた、文が書いてある行で数えます。迷うときは、縮めずに済む方（新しい .md の提案）を選びます。

1. **回答欄には結論だけを書く。** 結論を1〜3行で書き、その後ろに次の1行を足します（この行は1〜3行に含めません）。
   `> 詳しい説明は長くなるため、別の .md にまとめることを提案しています。`
2. **報告で提案する。** 質問ごとに、次を1〜2行で伝え、最後に「作りますか？」と聞きます。複数あるときは、どれを作るか選べるように番号で聞きます。新しい .md は、了承されるまで作りません。
   - 作るファイル: 元のファイルと同じフォルダに `<元のファイル名>-<番号>.md`（例: `01_architecture-Q1.md`）
   - 書く内容: 何をどこまで説明するか
3. **了承されたら作る。** 新しい .md には、次の順で書きます。
   - 見出し（`# ` で始まる、質問の内容を表す題）
   - 元のファイルへのリンクと、対象の文・質問の引用（下の例のとおり。`[!QUESTION]` や `[!ANSWER]` は付けません）
   - 説明。省略せず、見出しで区切って、順を追って書きます。長さの上限はありませんが、同じことを繰り返して水増ししません。表・箇条書き・コードブロックも使えます（HanaME で表示できます）
   - 書き方は回答欄と同じです。専門用語はかみ砕き、確かめられなかったことは最後に1文で書きます

   ```markdown
   # イベントソーシングと CQRS とは何か

   元のファイル: [01_architecture.md](01_architecture.md)

   質問の対象の文:

   > DBはイベントソーシングで永続化し、CQRSで読み取りモデルを分離する。

   質問:

   > イベントソーシングも CQRS も初めて聞きました。一から教えてください。

   ## 結論
   ```
4. **回答欄をつなぐ。** 回答欄の「提案しています」の行を、`> 詳しくは [ファイル名](ファイル名) にまとめました。` に置き換えます。HanaME では、このリンクから新しい .md を開けます。
5. **断られたら**、回答欄の「提案しています」の行だけを消します。

## 回答の例

```markdown
> [!ANSWER] Q1
> 「ハンドラ」は、届いた命令を受け取って、担当の部品に渡す係のことです。
>
> 画面から「注文する」という命令が来たら、ハンドラが中身を確かめ、注文を管理する部品（アグリゲート）に渡します。
```
